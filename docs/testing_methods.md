# Сравнение методов тестирования ЛР № 4

| Метод | Что показал на matrix_symmetry | Преимущество | Ограничение |
|---|---|---|---|
| Анализ граничных значений | Приняты размеры 1 и 2, отклонены 0 и −1. Отличие на один шаг `float` нарушает точную симметрию | Проверяет места смены поведения небольшим набором входов | Контракт обмена и внутренние ветви требуют отдельных проверок |
| Покрытие решений и условий | Подтверждены два сообщения о симметрии и оба исхода проверки длины списка | Показывает, какие исходы логики действительно выполнены | Само выполнение ветви не подтверждает корректность результата |
| Комбинаторное покрытие условий | В поле `values` сопоставлены тип данных и длина для четырёх комбинаций | Помогает выявить зависимость результата от состава условия | При коротком вычислении часть условий пропускается, а число комбинаций растёт с числом условий |
| Интеграционное тестирование | JSON-запрос проходит преобразование, вычисление в отдельном процессе и запись ответа | Проверяет согласованность модулей, кодов завершения и форматов | Сквозные запуски медленнее и сложнее локализуют дефект |
| Регрессионное тестирование | Защищает точное сравнение чисел, обработку версии JSON и сохранность запроса BR-01 | Повторные прогоны сохраняют уже подтверждённое поведение при правках | Требует актуализировать ожидаемые результаты при изменении требований |

Для проверки новых правил размера и числовых данных подойдут граничные
сценарии и модульные тесты. При изменении логической проверки полезно
сопоставить входы с исходами её условий. Изменение формата JSON или
запуска процесса требует интеграционного прогона. После каждой правки
стоит запускать регрессию и полный набор в GitHub Actions.
