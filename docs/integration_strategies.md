# Сравнение стратегий интеграции

## Нисходящая

Порядок: от управляющих модулей к нижним компонентам.
Преимущество: рано проверяется логика управления системой.
Недостаток: для отсутствующих нижних модулей нужны заглушки.
Применение: системы с выраженной иерархией управления.

## Восходящая

Порядок: от нижних компонентов к управляющим модулям.
Преимущество: сначала проверяются реальные базовые операции.
Недостаток: нужны драйверы, общая логика проверяется позднее.
Применение: библиотеки, вычислительные и инфраструктурные модули.

## Сэндвич-интеграция

Порядок: верхняя и нижняя части проверяются отдельно,
затем соединяются через согласованные интерфейсы.
Преимущество: рано проверяются и управление, и вычисления.
Недостаток: нужны драйверы, заглушки и согласование частей.
Применение: многоуровневые системы с понятными границами модулей.

## Риск-ориентированная

Порядок: первыми соединяются наиболее рискованные компоненты.
Преимущество: сложные проблемы обнаруживаются раньше.
Недостаток: необходимо правильно оценить риски и зависимости.
Применение: проекты с новыми технологиями и внешними интеграциями.

## Функционально-ориентированная

Порядок: система интегрируется по отдельным функциям пользователя.
Преимущество: каждая завершённая функция даёт проверяемый результат.
Недостаток: одна функция может затрагивать много общих модулей.
Применение: приложения, которые развиваются по пользовательским задачам.

## Т-образная

Порядок: сначала проверяется один сквозной путь через все уровни,
затем расширяются возможности компонентов.
Преимущество: рано проверяется работа архитектуры целиком.
Недостаток: первый путь не охватывает все функции и ошибки.
Применение: проекты, где важно рано проверить сквозное взаимодействие.

## Выбор для проекта

Для варианта 3 используется сэндвич-интеграция.

Вычислительный модуль сначала проверен тестовым драйвером.
Управляющая часть проверена с заглушкой вычислений.
После этого подключены реальные вычисления.

На уровнях 2 и 3 взаимодействие расширено JSON-обменом,
отдельным вычислительным процессом и обработкой таймаута.

Стратегия позволила последовательно проверить части программы,
а затем их совместную работу.
